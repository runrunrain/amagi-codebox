## Findings

### F01｜Major｜mutation 释放与门禁缓存刷新之间能启动半切换会话

**定位**：`claude_accounts_launch.go:79-104,206-241,274-292`；`claude_accounts_facade.go:240-241,397-404`；`internal/claudeaccounts/swap.go:73-104`。

**触发**：已管理池发生部分写入失败且 journal 保留。Service 返回前释放 mutation admission；App 仅在 Service 返回之后调用 `refreshClaudeAccountsCache`。在两者之间插入桌面 launch（或 remote admission 检查）。另一种入口是 launch 已读出 managed，尚未取得 admission 时 mutation 完成。

**实际影响/证据**：launch 只读旧缓存，无 journal、旧 generation；coordinator 只知道 mutation 已释放，不知道池已 blocked。`beginClaudeCredentialsClaim` 取 admission 后不重读 ready；外部 recheck 和 embedded 提升只比同一缓存的 generation。失败事务通常不增加 generation，因此三者均可能放行混合认证。首次 capture/BeginEnrollment 也有 absent/managed→新状态的类似交接窗口。remote 在 absent 时构建的不含凭据 admission 的旧计划，还能绕过仅在 admission 循环中的 freshness 检查（`internal/remote/remote_session_adapter.go:553-590`）；executor 没有独立的凭据 ready 校验。

**最小修复**：在 mutation 释放之前发布权威 ready/blocked/generation；launch 取得 claim 后再次校验同一权威状态。对 absent→managed 的旧计划、无凭据 admission 的受影响计划也在执行边界校验，不只检查已有 kind。用精确屏障覆盖「失败留 journal→释放→launch→缓存刷新」及「absent 计划→首次 capture→执行」。

### F02｜Major｜首次启用前已运行的 CodeBox 会话被静止检查豁免

**定位**：`claude_accounts_launch.go:208-209,367-421,428-430`；`internal/claudeaccounts/service.go:464-474`。

**触发**：无池时启动 Claude/Pi（不持凭据 lease），保持运行，再首次 capture / begin enrollment / swap。

**实际影响/证据**：Quiescence 把 `Sessions.List()` 的所有 PID 及后代标为 attributed，并无条件跳过这些消费进程。它假定 coordinator 已有对应 lease，但 absent 时从未创建该 lease。于是 mutation gate 没有用户、观察器也跳过已有会话，能在旧 Pi/Claude 仍运行时启用管理并继续换号。UI 的“请先退出”不能代替后端 enforcement；这直接违反 §1.3-7 和 §4.3 的所有消费进程静止条件。

**最小修复**：启用/恢复时纳入先前已运行的受影响会话；静止检查不能仅凭“属于 CodeBox”豁免，必须证明对应进程树已结束或持有会阻止 mutation 的有效 lease。正式测试从 absent 的真实启动状态进入 capture，而非预置 managed cache。

### F03｜Major｜journal revision 从未用于最终复核，二次 harvest 的 before 也未更新

**定位**：`internal/claudeaccounts/swap.go:107-131,149-151,170-190,226-255`。

**触发 A**：最终一次 source read 后、取得 Pi 短锁前，原生槽位刷新为 A′。**触发 B**：第一次 harvest 后到 `current2` 之间发生刷新，代码进入第二次 harvest；随后第一处写入失败或进程崩溃。

**实际影响/证据**：A 中 `ExpectedRevisions` 只被存储/赋值，取得原生锁后没有任何比较即 Patch，覆盖未回收的新 token。B 中第二次 harvest 的 OwnedProjections 返回值被 `_` 丢弃，`journal.Before` 仍用第一次的 `sourceOwned`，而 `ExpectedRevisions` 已是新版；原生 A′ 对 before/after 均 unknown，原本应全 before 的可恢复事务被卡死。不是要求 hash 充当全局 CAS，而是设计已要求的最后复核和 before 一致性根本缺失。

**最小修复**：在短提交锁内复核当前整文件/受管 revision；漂移则退出/重采集，不能直接写。每次重新 harvest 必须同步替换 sourceOwned/sourceRevs，journal 的 before 和 expected 必须来自同一次快照。

### F04｜Major｜取消录入会清除唯一恢复标记并错误重开启动入口

**定位**：`internal/claudeaccounts/service.go:435-460`；`claude_accounts_launch.go:98-104`；`claude_accounts_facade_test.go:322-359`。

**触发**：开始录入 B 后，原生已是 B 或 CC/Pi 混对，capture 失败，然后取消录入。

**实际影响/证据**：CancelEnrollment 不取 mutation gate、不检查 native，无条件清 transaction；policy 随即回 managed。池仍显示 active=A，实际可消费 B 或混合认证，且 UI 不进入 needs-reconcile。§4.1 明确要求漂移时保持 needs-reconcile。现有 `TestFacade_BeginEnrollmentAndCaptureFlow` 恰好用原生 B+capture 失败触发此场景，却断言取消后无 journal、policy=managed；本轮复跑该测试仍绿，说明它锁定了错误行为。

**最小修复**：取消走 mutation/静止门，读取并分类当前投影；仅证明仍与活动源一致时清除 enrollment，变化/无法验证时保留可人工恢复的状态与证据。修正相反的测试断言。

### F05｜Major｜换入目标只检查旧身份证据，刷新后的双 grant 未验证

**定位**：`internal/claudeaccounts/harvest.go:128-175`；`internal/claudeaccounts/service_swap_test.go:155-185`。

**触发**：目标 standby 自录入后已被撤销/失效，或 Pi grant 刷新后需证明新 token 身份。

**实际影响/证据**：ensureTargetReady 仅比较 capture 时的 UUID 字符串并检查存储的 health，整个函数不调用 IdentityProvider。即使刚刷新出新 token，也直接写入生产槽位并宣布切换完成；未过期但已撤销的 token 同样会被当 ready。设计 §4.4 明确“准备目标…验证目标双端身份”。现有 expired-target 测试没有给 `pi-a-fresh` 建立任何 profile 映射仍成功，直接证明此门不存在（本轮领域测试复跑通过）。

**最小修复**：刷新存池后、原生写入前分别验证目标两 grant，与目标身份/组织及目标本地 identity 配对；失败不写原生。增加刷新后 identity 不可验证/不一致和未过期已撤销的反例。

### F06｜Major｜恢复未完成也返回 done；restore-source 全 before 会留下 journal

**定位**：`claude_accounts_facade.go:254-258,541-579`；`internal/claudeaccounts/reconcile.go:352-360`；`internal/claudeaccounts/swap.go:60-68`。

**触发 A**：journal 存在，complete-target 遇到运行 lease 或外部进程。**触发 B**：崩溃于 prepared 后、第一处写入前，原生仍全 before，点击 restore-source。

**实际影响/证据**：A 中 RecoverAtStartup 返回 `roll-forward-pending + ReasonCode` 且 err=nil；facade 丢弃 outcome，通用 runner 标 `done/commit/changed=true`，UI 宣告恢复成功但 journal 和阻塞仍在。B 中 target=source=当前 active，Swap 在 reconcile 之前命中 no-op 返回，同样 done，但 journal 未清、入口永远仍 blocked。`complete-target`/`restore-source` 还都没有实际验证传入的 expectedRevision（参数仅进入 digest），陈旧恢复命令可作用于已变化的事务。

**最小修复**：恢复动作消费 outcome，pending 映射 blocked 而非 done；done 必须以动作结果、journal 已清、三处一致为依据。先处理未结事务再允许 no-op；在同一锁内校验 expectedRevision 和所选 journal。

### F07｜Major｜remote/restart 与外部 Claude 路径漏掉受管身份环境边界

**定位**：`launch_planner.go:309-358`；`pi_login_launch.go:362,394-425`；`app.go:2724,2838-2841`；`internal/launcher/service.go:110-144,263`。

**触发**：受管理池中选择 B，通过 remote create/restart 启动，并继承 `CLAUDE_CODE_ACCOUNT_UUID=A`、`CLAUDE_CODE_DEVICE_ID`、`CLAUDE_CONFIG_DIR` 或 `CLAUDE_CODE_OAUTH_TOKEN`；或通过桌面外部终端路径启动 Claude。

**实际影响/证据**：身份清理函数唯一 Claude 调用在 embedded 分支。Claude planner 仅增加 admission，从未调用该清理；Pi login planner 调 `piLoginEnvOverrides` / `piLoginReAnchorSpec` 时未传新增 extra keys。外部 Claude 直接 `external.LaunchGuarded`，没有 managed extra env 输入；旧 ComputeEnvOverrides 只清 ANTHROPIC_API_KEY/AUTH_TOKEN/BASE_URL，不清上述变量。lease 能防换号，不能修正启动时已错误的身份/根/认证，报告 1b §一“R3 ✅”不成立。此为代码中确定的路径遗漏，不依赖真机 profile 协议。

**最小修复**：复用一个受管执行边界到桌面 embedded/external、remote create/restart 的 Claude/Pi；必要时拒绝不能证明 canonical 身份的启动。将身份清理置于 shell 初始化之后，不能用观察器代替。以真实计划/最终命令断言这些键不可能覆盖身份。

### F08｜Major｜首次录入、第二账号核对和恢复的异步失败在界面被隐藏

**定位**：`frontend/src/components/provider/ClaudeAccountsSection.vue:36-124,242-244,399-405,444-454`。

**触发**：首次 capture 返回 operationId 后最终 IDENTITY_MISMATCH/IDENTITY_UNVERIFIED；或 enrollment capture 失败；或 recovery operation 失败且池仍 needs-reconcile。

**实际影响/证据**：异步错误只进入 `store.operation`；`errorText` 虽计算了它，但 operation/error 横幅只在最后的 managed/error `<template v-else>` 内。absent、enrolling、needs-reconcile 分支全不渲染；这些错误又不是同步 throw，因此 action catch/toast 不触发。尤其“两端不是同一账号不入池且必须明确指出”的主路径，用户只看到原来的向导和“正在核对”提交提示，看不到失败原因。phase1c 声称组件反馈完整，实际纯 view/store 测试没覆盖模板分支。

**最小修复**：把 operation 过程/失败反馈提到各状态共用区域，或逐分支渲染；以真实组件交互验证 absent/enrolling/reconcile 的异步错误，而不只测试文案函数。

### F09｜Major｜重启/刷新后无法继续持久化 enrollment

**定位**：`claude_accounts_facade.go:96-108,317-325`；`frontend/src/stores/claudeAccounts.ts:71,126-139,247-259,264-271`；`ClaudeAccountsSection.vue:422`。

**触发**：BeginEnrollment 已持久化，主上在原生两端登录 B，然后刷新 Wails 页面或重启 CodeBox。

**实际影响/证据**：enrollmentId 只在前端内存保存；GetClaudeAccounts 只返回 state=enrolling，不返回可续接 ID。重建 store 后 enrollment=null，向导默认 login，而“下一步”函数要求 enrollment 非 null，点击也不推进；即使直接调 captureEnrolled 也抛“尚未开始录入”。后端却要求精确匹配 TxnID 才能保存 B。安全退出依赖有缺陷的 cancel 路径（F04），正常录入不能续接。

**最小修复**：安全 DTO 返回持久化 enrollment 的 ID/阶段，刷新重建向导；后端仍校验 revision/TxnID。不把所有池秘密放进 DTO。覆盖开始录入→重建 App/store→继续保存。

### F10｜Major｜已存在账号池被删除时被当作从未启用，保护静默消失

**定位**：`internal/claudeaccounts/poolstore_keychain_darwin.go:92-95`；`claude_accounts_launch.go:93-94,546-555`。

**触发**：管理已经启用，Keychain 账号池项被外部删除；随后 UI refresh，或应用重启。

**实际影响/证据**：errSecItemNotFound 一律返回 nil,nil，无历史存在性标记；刷新覆盖缓存为 nil，launch policy=absent，账号 UI 也变未录入。§3.3 要求已创建池的 missing 必须区别从未创建，停管告警，不能默默重新生成空池。此路径还能使再次 capture 按空池执行，丢失对旧池/事务的认知。该结论来自明确 missing 分支，不是对 Keychain 弹窗行为的推测。

**最小修复**：维护不含秘密的“曾初始化”标记/可校验存在性记录；missing 报 POOL_MISSING 并 fail closed，恢复/重建须显式确认，不覆盖原生。区分本运行周期和重启后的缺失。

### F11｜Major｜Claude 原生项消失后会 Add 重建，违背 ACL/缺项停止契约

**定位**：`internal/claudeaccounts/nativecc_darwin.go:69-85`。

**触发**：已定位/读取原生项后，它在 update 再次 find 前被删除（外部登出、删除或竞争）。

**实际影响/证据**：C `amagi_cc_update` 的 errSecItemNotFound 分支调用 `SecKeychainAddGenericPassword`，把新 token 写入新项而不是停止。新项没有原项 ACL，且静默重建已消失的原生登录；与 §3.1/§4.4 明确“更新现有 item、不得删后重建、缺失 blocked”及本文件注释相反。fakeKeychain 的 UpdateItem 缺项返回错误，未仿真这个真实 C 分支，所以 fake 测试全绿不能支持生产声明。

**最小修复**：原生 update 的 missing 只返回稳定错误，禁止 Add fallback。池首次创建与原生 credential update 不是同一权限语义；两套 API 必须分开。

### F12｜Major｜进程观察器漏掉 Pi 官方 RPC 入口的进程标题

**定位**：`claude_accounts_launch.go:334-352,405-415`。

**触发**：CodeBox 外存在使用 canonical agent root 的 Pi RPC 进程，系统进程表显示其标题 `pi-rpc`；此时尝试切换。

**实际影响/证据**：观察器逐字段 basename 只能匹配精确 `pi/claude`（及 exe），`pi-rpc` 不匹配，Check 返回 nil。为排除“正常入口会改标题所以实际仍是 pi”的反证，本轮只读核对实际安装源码：`/Users/run.mao/.local/share/fnm/node-versions/v24.21.0/installation/lib/node_modules/@earendil-works/pi-coding-agent/dist/rpc-entry.js:5-10` 明确设置 `process.title = APP_NAME + '-rpc'` 并运行 `main(['--mode','rpc',...])`；该安装 `dist/config.js:471` 默认 APP_NAME 为 pi。未执行真实 RPC，也未读取用户认证。这个入口并不是非相关 Node 程序，却会从扫描中漏掉；其仍存活时原生刷新/身份缓存风险没有被阻止，违反 §4.3 的相关消费者静止条件。1b 报告“宁可误报不漏报”不成立。

**最小修复**：识别官方 RPC/可配置名称及可验证 executable/script/package 路径；相关但无法确认的启动形式返回 uncertain。以官方入口的进程表 fixture 覆盖，不只用 `/bin/pi`。保留人工使用约束，不宣称 ps 可阻止随后外部启动。

### F13｜Minor｜Pi 刷新重建条目，丢失原有未知字段

**触发**：池内 Pi anthropic 条目含当前版本未知的扩展字段，换入前发生 refresh。

**实际影响/证据**：BuildPiAnthropicEntry 从零只构造 type/access/refresh/expires，整体替换旧条目；与 §3.1 的未知字段保留契约不符。已证明字段丢失，尚无证据断言这些未知字段在当前 Pi 有关键运行语义，故不升级 Major。

**最小修复**：在原 anthropic JSON 上字段级更新已拥有的 token/expiry，保留其余字段；加入含扩展字段的 refresh 用例。

### F14｜Minor｜RemoveAccount 忽略 expectedRevision

**定位**：`internal/claudeaccounts/harvest.go:357-385`。

**触发**：UI 持有 revision=N 的列表，另一操作更新账号快照/别名后，以旧 revision 提交删除该 standby。

**实际影响/证据**：参数完全未参与校验，删除仍成功；与同类 Rename/Capture 的乐观锁语义及 §7.2 接口不一致。当前不删除活动账号，不直接写原生，影响限于保存的 standby 数据。

**最小修复**：锁内、删除前检查 pool.Revision；补 stale revision 零删除负向用例。

### F15｜Minor｜operation 缓存淘汰仍会删除运行中操作

**定位**：`claude_accounts_facade.go:167-187`。

**触发**：缓存超过 128，最旧 victim 尚未关闭 done（可经多个后台请求排队触发）。

**实际影响/证据**：select 的 default 将 victim 追加队尾后 `break` 仅退出 select，仍继续执行下面 delete(op) 和 request 索引删除。于是运行中 operation 查询变 NOT_FOUND，相同 requestId 不再返回原操作，破坏所声明的幂等/在途不淘汰规则。达到阈值后可复核；本轮未作压力运行，且 generation 校验仍限制重复 swap 的写入，故按局部边界 Minor。

**最小修复**：仅删除已完成 victim，正确跳过运行中项，并对全为运行中的情况限制入队/显式 busy，防无限循环或无界缓存。
