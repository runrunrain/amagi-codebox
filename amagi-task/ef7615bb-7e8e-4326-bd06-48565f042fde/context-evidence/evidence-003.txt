## 三个讨论问题的简要回答

**① 当前 WSL 是否独立 CLI 与配置？** 是，但配置是**受管镜像而非孤儿副本**。CLI（claude/opencode/codex/pi）经 envcheck「WSL 内的 CLI」卡片以 npm 包装进 distro（`wslsetup/service_windows.go:148-217`）；配置由 CodeBox 单向投影到 distro `$HOME`（pi/omp `~/.pi/agent/models.json`、opencode `~/.config/opencode/amagi-codebox.json`、Claude/Codex 键级导入+skills/commands 选中复制，`resources.go:1-10`），插件不复制实体、在 distro 内原生重放 `pi install`（`plugins.go:1-13` 规则2）。用户不需要手工维护第二份——启动时自动补漏/刷新。

**② 复用 Windows 配置的边界在哪？** 实时复用的只有：API key/代理/CLAUDE_/PI_ 等**环境变量**（WSLENV 每次启动注入，无副本落盘，`wsl.go:419-426`）与 pi OAuth `auth.json`（双向新者为准同步，`wsl_pi_login_sync.go:6-16`）。其余均为**转换后的副本**：MCP server 路径转 /mnt/c、settings 只导白名单标量（permissions/hooks/env 明确排除，`claude_adapter.go:49-66`），`.claude.json` 的 projects 等机器状态“永不跨界”（`claude_adapter.go:41-43`）。

**③ 完全不装 Linux CLI 的语义差别？** 那只能走 WSL interop 调 Windows exe（`claude.exe` 在 Windows 文件系统上读 Windows 配置）——仓库无此路径，且与现有架构相反（resolver 短路 + wslsetup 安装卡）。直读方案还有实证约束：9P/UNC 写入无 POSIX 权限位（0600 不可表达，`wsl_home.go:14-18`）、DrvFS 挂载有性能/行为 advisory（`app_drvfs_advisory.go:1-9`）、跨界 env 中 Windows 盘符路径值必须剥离（`wsl_agent_config.go:30-35` 证据 B3/T6）——这三点均与“把 HOME/配置指到 /mnt/c 直读”冲突。

## 可行性结论（推断，供下游裁决）
- 用户目标中“**效果上不重复维护配置**”：已基本实现（托管分发自动化），差距只在副本语义带来的延迟/冻结边界（WSL 手改冻结、启动才刷新）。
- 字面目标“**WSL 会话直接加载 Windows 侧配置文件**”：未实现；需新增 HOME 重定向/软链或 interop 调 exe 方案，且会绕开现有密钥同意门（`coordinator.go:333-373`）与权限/路径防线，属架构级变更。
