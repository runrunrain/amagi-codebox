# 需求分析 · 澄清式文档撰写

> 写给使用本技能的 Agent。

## 一、这个技能做什么

把一份"用户给的原始意图"（一段思考、一个需求描述、一次对话里的零散想法），整理成一份 **讨论稿式的需求澄清文档**。

讨论稿的灵魂是：**它是写给用户去纠正的，不是拿来签字交付的。** 它的价值不在"一次写对"，而在"把模糊的地方都摆到台面上，让用户在反复讨论中把真实需求逼出来"。它是后续正式文档（设计、方案、计划）的 **前置对齐材料**，不是正式文档本身。

**这个技能不做什么**（搞混了就会跑偏，这点很重要）：

- 不写技术方案、技术选型、架构设计
- 不写数据结构、接口定义、伪代码
- 不写实施计划、阶段划分、里程碑、排期
- 不替用户做决策、不替用户填留白
- 不追求"一次成型的完美文档"

以上这些，要么是用户该定的（决策），要么是后续设计文档该做的（方案/计划）。需求分析阶段越界去做，就会把"澄清"变成"擅自拍板"，反而偏离用户真实意图。

## 二、什么时候用 / 不用

**用**——当任务的本质是"意图还没收敛清楚"：

- 用户给了想法，但里面有多处模糊、留白、未定义
- 不同目标之间感觉有张力或矛盾，先要对齐方向
- 用户自己也还没完全想清楚，需要被引导着说清楚
- 动手做方案之前，需要先把"到底要什么"对齐

**不用**：

- 意图已经清楚，只剩执行（直接做）
- 简单的单点改动（直接做）
- 用户明确要直接产出方案/架构/代码（那不是需求分析，是设计/实现）
- 已经有现成的需求文档，只需后续步骤（别重复分析）

## 三、核心理念（为什么这样写）

理解这几条"为什么"，比记住任何模板都重要。模板会限制你，理念不会。

1. **讨论稿，不是规格书。** 写它是为了被讨论、被纠正。所以语气要像对话（"我理解的对吗""这点想跟你确认"），不要像宣告。要主动邀请用户打断。如果用户读完觉得"你都定好了还问我干嘛"，讨论稿就没起到它的作用。

2. **忠实于原始材料，区分"事实"和"推导"。** 用户明确写过的，才当事实。从事实推导出来的，要标成"我的推导，待你确认"。用户没写的，不编造——标"待确认"就好，不替用户脑补。这是诚信底线：只要有一处把猜测写成了事实，用户就很难再信任整份文档。

3. **不替用户决策。** 需求里的留白（没定义清楚的地方、没拍板的取舍），要诚实暴露成"待确认"，给背景和选项供参考，但 **不替用户填空**。替用户填空是需求分析最常见的越界——它把"我猜你想要"伪装成"你确实想要"。

4. **给方向，不给方案。** "处理思路"只说往哪个方向走（例如"结果应该由一方统一算，避免各端分歧"），不说具体怎么做（不指定用什么框架、什么算法、什么库）。方案留给后续设计文档。越早陷入"怎么做"，就越晚发现"要的其实不是这个"。

5. **诚实，包括对自己的误判。** 发现原始材料内部有矛盾、发现自己之前理解错了、发现某个外部参考越权了（把没写过的东西当成了需求）——都要如实指出。需求分析的可信度建立在"不掩盖问题"上；你诚实，用户才敢信你的梳理。

## 四、文档骨架（参考，按需调整）

以下是骨架。**它不是必须逐条填的表格**——根据实际材料裁剪：材料里没有的部分就删掉，材料特别丰富的部分就展开。

1. **开头：定位说明**
   一两句话说清这份文档是什么（讨论稿）、不是什么（不是方案/计划）、怎么用（请用户纠错）。先管理预期，避免用户把它当成最终交付。

2. **核心意图（一句话锚点）**
   从原始材料里提炼"这件事本质上想要什么"，一两句话讲清。这是后面所有取舍的锚。**因为是你的提炼，要请用户确认对不对。**

3. **用户想要的**
   - **显性的**（材料里明确写过的）：忠实梳理，不夸大不缩小。可用表格。
   - **隐性的**（你从显性需求推导的）：单独列出，每条标"推导，待确认"。让用户一眼看出哪些是他说的、哪些是你猜的。

4. **用户不想要的 / 暂缓的**
   材料里点名排除或暂缓的内容，忠实记录。如果是你推导的边界偏好，也要标出来，别混成用户原话。

5. **当前的真实困难**
   这是文档很重要的部分，把"难在哪"讲透：
   - **需求留白**：哪些决定成败的关键语义其实没定义
   - **现状/资源约束**：手头有什么、缺什么、现有的东西能帮多少
   - **目标间的张力**：哪些用户想要的东西之间天然打架
   讲困难时 **不给解决方案**（那是思路部分的事），只把困难摆清楚。

6. **方向性的处理思路**
   针对困难，给 **方向性** 的建议（往哪走），不给具体方案（怎么做）。讲清"为什么这个方向合理"。明确这是建议，最终方向由用户定。

7. **待确认清单（文档重心，详见下一节）**
   把所有需要用户拍板的问题列出来，分优先级，每项给足背景。这是讨论稿的核心载体。

8. **与其它材料的关系 / 建议的讨论顺序**
   说明本文档和原始材料、其它参考文档的关系；建议用户从哪里开始跟你讨论。

## 五、待确认清单怎么写好（这是文档重心）

待确认清单不是"问题列表"，是 **讨论的抓手**。写得好，用户能轻松逐项给你方向；写得差，用户面对一堆空泛问题不知从何答起，干脆不答。

每一项待确认，尽量包含：

- **问什么**：一个清晰、具体的问题。不要"这个怎么做"，要"撤退和普通移动要不要区分"。
- **为什么重要**：这个问题不解决，会影响什么。让用户理解为什么值得现在想。
- **目前是什么情况**：是留白 / 矛盾 / 有哪些选项。
- **可选的方向**（供参考，不替用户定）：列出可能的选项，简述每个的取舍。
- **影响什么**：这个决策会牵动哪些后续选择。

**分优先级梯队**：把问题按"不定就没法开始 → 定了才好往下 → 最后再定"排成几个梯队。告诉用户"不用一次答完，先过第一梯队"。这降低用户的回复门槛，也符合"反复讨论"的精神。

**标注类型**：每项标清是 【待确认】（要用户拍板）、【待澄清】（信息不够，要用户说明）、还是 【待调研】（需要去查证后才能定）。类型不同，处理方式不同。

## 六、质量自检

交付前对照检查：

- [ ] 事实和推导分开了吗？推导都标了"待确认"吗？
- [ ] 需求里的留白都诚实暴露了吗？有没有替用户填空？
- [ ] 待确认项好答吗？每项都有背景/选项/影响，不是空泛提问？
- [ ] 有没有越界写了技术方案/数据结构/架构/阶段计划？（有就删）
- [ ] 语气是对话式的吗？有没有邀请用户纠错？
- [ ] 发现的矛盾、自身的误判，有没有如实指出？
- [ ] 开头说清了"这不是最终交付、是讨论稿"吗？

## 七、工作流程

1. **读全原始材料**，以它为唯一真相源。没读全就动手，必然脑补。
2. **提炼核心意图**（一句话锚点）——这是你的理解，待用户确认。
3. **区分显性 / 隐性 / 留白**：哪些是材料明说的、哪些是你推导的、哪些是没说的。
4. **识别困难**：留白在哪、约束是什么、哪些目标打架。
5. **给方向性思路**（不给方案）。
6. **列待确认清单**：分梯队，每项给足背景。
7. **标注定位**：说清本文是前置材料，不是交付。
8. **交给用户，邀请讨论**；据反馈多轮迭代（见第八节"多轮讨论与收束"）——讨论稿会在几轮对话后趋于准确，这是正常的，别指望一版定稿。

## 八、多轮讨论与收束（讨论稿的核心用法）

讨论稿不是一版定稿，它的价值在"多轮迭代逼近真实需求"。第一版往往是"把模糊全摆出来 + 列一堆待确认"，然后通过几轮来回收敛。规范如下：

### 每轮更新要做的事

拿到用户反馈后，这一版做四件事：

1. **固化已确认的**：用户明确回答过的，从"待确认"升级为"明确需求"。不再是问句，而是陈述。
2. **诚实补入新问题**：用户的回答常常**引出新留白**（例如确认了"要做补给"就引出"粮食怎么消耗"）。要主动捕捉、补进待确认清单——不能只收不加。只固化不补入，会漏掉真实存在的模糊。
3. **维护"已确认决策汇总"**：用一张表/列表集中呈现历轮敲定的结论，方便用户一眼复核"我都说了啥"。
4. **给收束判断**：每版末尾说清"核心齐不齐、还剩多少待确认、是否接近收束、下一步问什么"。降低用户的决策负担，也让用户知道还要聊几轮。

要点：待确认清单的**净趋势是收敛**，但不必单调递减——新问题冒出来是正常的，诚实补入比假装没有强。

### 什么时候收束

满足这几条就可以收束：

- **核心需求齐备且自洽**（是一套连贯的"要什么"，不是零散问答的拼接）
- **无阻塞待确认**：剩下的都是配置/数值/下游细节，交给设计文档不卡住"做什么"
- 用户对剩余项**认可默认或已拍板**

不要为了"每个问题都答完"而拖延收束——有些细节本就该在设计阶段定。收束的标准是"做什么清楚了"，不是"所有问号都消除了"。

### 收束版（需求基线）怎么写

收束时产出一版"需求基线"，它和讨论稿的写法不同：

- **语气转变**：从讨论稿的试探（"我理解对吗""待你确认"）转为基线的确定（"这是已锁定的需求"）。去掉问句和征询口吻。
- **标记状态**：标题/开头标明"收束版 / 需求基线"。
- **加交接要点**：专门列一节"给下游（设计/方案文档）的交接要点"——把"要什么"翻译成"下游该解决什么"，让设计文档能直接接手。
- **清空阻塞待确认**：剩余项明确标注"交下游"，不再作为悬而未决的问句。
- **保留可修订性**：基线不是不可改的圣旨。说明"设计阶段若发现偏差可回头修订，但要记录版本与原因"。

### 版本管理与演进溯源

- 每版标版本号（v1 / v2 / ... / 收束版）。
- 每版开头放简短"更新说明"：本轮确认了什么、还剩什么。
- 收束版末尾保留演进溯源（v1→v2→...→收束），让读者看到需求是怎么收敛来的，也便于日后追溯某个决策的来龙去脉。
- 和用户的来回，尽量通过**文档**进行（用户写回答文档、你出新版文档），比零散对话更完整、可追溯。

## 九、反模式（常见错误）

- **写成技术方案/架构设计/实施计划** —— 最常见的跑偏。需求分析不解决"怎么做"。
- **把推导当事实，或替用户填空** —— 失去诚信，误导用户。
- **待确认项空泛**（"这个怎么处理？"）—— 用户没法答。要给背景和选项。
- **一次追求完美** —— 讨论稿的本质是被纠正的，第一版有盲点很正常，别为此把文档写死、写满。
- **只固化、不补新问题** —— 用户回答引出的新留白要诚实补入待确认，否则漏掉真实模糊。
- **该收束不收束 / 核心没定硬收束** —— 核心齐备就收束，别为细节拖延；反之核心没自洽别假装收束。
- **绑定具体业务内容** —— 本技能是通用方法论；范例可以具体，但方法论本身不绑定任何领域（软件、游戏、产品流程都适用）。
- **语气像宣告不像对话** —— 用户会觉得"你都定了还问我干嘛"。要真讨论。
